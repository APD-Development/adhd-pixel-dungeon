# Feasibility: reconstruct any floor of a finished run from its seed

Study only; nothing implemented. Based on `Dungeon.java`, `Level.create`, `RegularLevel`, `Generator`, `SpecialRoom`, quests,
`LevelGenerationHarness` (Phase 5 golden test) and the recorder.

## Verdict
- **Exact for floors 1..N when replayed in order under a fixed, documented context**: yes. The golden harness already regenerates
  floors 1..N headless, bit-identical (SHA-256 of the full saved level) from seed + challenges + class + context.
- **"The floor the player would have met" for a never-reached floor: not defined exactly.** A floor is not a function of (seed, depth).
  It depends on state left by earlier floors and by play. APD can offer the *canonical seed floor* (generated by an in-order replay
  with reference state), labelled as such, never as "what would have happened".
- Floors that were reached are already recorded (events 291-294, true identities). Replay adds value only beyond the deepest floor.

## What besides the seed decides a floor
Pure part: `Level.create` seeds from `Dungeon.seedForDepth(depth, branch)`; run-start state (scroll/potion/ring identities,
`SpecialRoom`/`SecretRoom` run lists, initial `Generator` decks) derives from `seed+1` in `Dungeon.init`.

Cross-floor state (forces replay of 1..N-1, in the real generation order):
- `Generator` decks/category probabilities, consumed by every draw (carried between floors).
- `Dungeon.LimitedDrops` counters (strength, upgrade, stylus, enchant stone, intuition stone, trinket catalyst, lab) drive `posNeeded`,
  `souNeeded` etc. (these also consume level RNG), plus `SpecialRoom.pitNeededDepth`.
- Quest state: `Ghost/Wandmaker/Blacksmith/Imp.Quest` (`spawned` flags set by earlier floors).
- Generation order: branch levels (mining 11-14, vault 16-19) are generated when entered; order changes deck consumption.

Contextual state (must be fixed or recorded):
- Run: challenges, hero class, `SPDSettings.intro()`, APD exotic chance (recorded in LEVEL_GENERATED), `Dungeon.chapters`.
- Hero-dependent: DriedRose petals (`rose.droppedPetals`), Cached Rations talent buff, `ShopRoom` bag/hourglass choice,
  `Notes` key records, `Statistics.amuletObtained`, mimic/hero items.
- Global to the install, not the run: journal `Document` pages found (decide which guide/lore pages are placed), `Bones` from other runs.
- Unseeded by design: floor 1-2 guide page placement (harness strips it); play-time loot (mob drops, bonus drops, chasm, resurrection)
  which also draws from the decks and so shifts later floors in the real run.

## Required data
Already stored per run: seed, challenges, class, exotic chance, per-floor LEVEL_GENERATED (LimitedDrops, deck counts, guide pages
found, hero items, build attempts) and ITEM/MOB_GENERATED. Missing for exactness: install journal-page state per run (only "guide
pages found" at level time), hero talent/rose state per arrival, branch-entry order, play-time deck draws. These can be *validated*
against replay (LEVEL_GENERATED counters give a checkpoint per reached floor) but cannot all be restored.

## Safest architecture
1. Only for runs with a terminal outcome and a recorded seed (same finished-only gate as Phase 7 disclosure). Never for the active run.
2. Replay engine = the harness path promoted to production: one `FloorReplay` that, outside any game, sets the reference context,
   runs `init`-equivalent setup and `newLevel()` for floors 1..N in order, returns a read-only `Level` summary (rows for a new
   dataset, e.g. "Seed floors": items with true identity, mobs, features), then discards everything.
3. Isolation is the hard part: generation mutates ~15 statics (Dungeon, Generator, LimitedDrops, quests, SpecialRoom, Statistics,
   Actor ids, Notes, Random stack, `TargetedCell`), and `Dungeon.init` also resets `Badges` and calls `ApdRecorder.onNewRun`.
   Required: a replay-only init (no badges, recorder/ApdGen off, no hero live), a full save/restore of those statics (bundle round
   trip), and refusing to run while a game is loaded in memory (UIMSD is opened from title/menus, not from GameScene). Run on a worker
   thread; verify headless-safe on Android (no sprites/textures during `create()`; needs API 26/34 device test).
4. Results cached in the derived store keyed by (seed, context id, replay version); an engine/game version bump invalidates.

## Risks and limits
- Exactness is relative to the stated context; label every row "canonical seed floor (reference state)". Runs that used bones,
  daily seeds, different journal state, branch order or heavy play-time loot will differ on later floors.
- Maintenance: any upstream SPD change to generation changes the output; the golden fingerprint file is the guard.
- Cost: generating N floors sequentially ~ hundreds of ms each; floor 26 needs 25 predecessors. Cache results.
- Statics isolation bug could corrupt a live game: highest-severity risk; needs mutation-checked tests (state identical before/after).
- Spoiler policy: revealing future floors for a *finished* run is mild (the seed can be re-entered as a custom seed), but still needs
  your approval.

## Recommended approach
Phase A (small): promote the harness to a `FloorReplay` with replay-only init and a statics snapshot/restore, plus tests: golden
equality with the harness, state-before == state-after, refuses when a run is active/unfinished, works on API 26/34.
Phase B: "Seed floors" dataset (floor, item true identity/location/room, mobs, special rooms) through the existing query/disclosure
architecture, deepest-reached floors cross-checked against recorded events. Phase C (optional): comparison "recorded vs canonical".
